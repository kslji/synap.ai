Two cooperating concerns live side-by-side:
- `deploy/` is a self-contained single-VM deployment manifest. `docker-compose.yml` composes five services — Caddy (reverse proxy on :80/:443), the Python API built from `../services/api`, SearXNG search, Valkey cache, and pgvector-backed Postgres — with healthchecks, named volumes (`caddy_data`, `pg_data`), and an initdb directory (`initdb/01_schema.sql`). `Caddyfile` forwards all traffic to `api:8000` and is mounted read-only; `searxng/settings.yml` configures the search engine; `.env.example` documents every runtime secret (JWT, SMTP, R2, Stripe/Razorpay webhooks, licence keys). A separate `docker-compose.dev.yml` provides a development variant.
- `.github/workflows/` contains the CI pipeline surface. `ci.yml` is the reusable entry point (triggered by PR/push and via `workflow_call`) that runs parallel jobs: desktop build/tests, web build/link-check, API pytest + Alembic head check, host unit checks, lint (ESLint + Ruff), typecheck (tsc + pyright), unit coverage, no-fabrication gate, security audit (npm audit, pip-audit, gitleaks), licence compliance, e2e Playwright smoke/model-reply, visual snapshots, bundle budget, and model/code-pack evals. `release.yml` composes these as needed and adds installer/offline-zip jobs per OS/arch plus a final `softprops/action-gh-release@v2` publish step. Other workflow files (`codeql.yml`, `eval-full.yml`, `installers.yml`, `model-eval-full.yml`) are modular pieces referenced from the top-level flows.
