Two cooperating subsystems live side-by-side:

- `loop.ts` is the entry point. `runCodeAgent(task, host)` drives a bounded (default 8-step) loop that calls `obtainCall` to ask the model for a tool invocation, dispatches it through `act`, and feeds observations back into the message history until `finish`, a limit, or parse failure. Tool schemas are declared in `tools.ts` (`CODE_TOOL_NAMES`, `codeToolSchemas`) and parsed via `parse-tool.ts` with a three-tier fallback: native tool-calling → JSON schema (`grammar.toolCallJsonSchema`) → GBNF grammar (`grammar.toolCallGbnf`). The `CodeAgentHost` interface abstracts the LLM call, project search, command execution, and user approval gate (`permission.ts`), so the loop itself never touches the filesystem or network directly.
- `completion/service.ts` implements inline completion as a debounced, per-session pipeline: windowing (`windows.ts`), snippet selection (`snippets.ts`), FIM vs prefix prompt building (`fim.ts`), caching (`cache.ts`), and post-processing (`post.ts`). It exposes `CompletionService.suggest` against a `CompletionHost` abstraction.
- Supporting modules split responsibilities: `workspace.ts` (read/list/run inside project root, no shell), `sandbox.ts` (child-process isolation), `budget.ts` (message trimming to token budget), `fix-loop.ts` (diagnostic classification and narrowed test commands for iterative fixes), `edit.ts`/`plan.ts`/`patch.ts` (diff planning and application), `project-search.ts` (semantic search integration), `checkpoint.ts`/`mode-store.ts`/`permission.ts` (user policy state).
- Dependency direction is inward: `loop.ts` depends on tools, workspace, permission, budget, grammar, parse-tool; `completion/service.ts` depends only on its sibling helpers. Neither subsystem imports from the rest of the desktop app — they communicate outward via the injected host interfaces.
